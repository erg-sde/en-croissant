# State of the art and failure modes of LLM/NN chess commentary; grounding techniques; open-source tactical-motif detection algorithms; and the deterministic facts available in en-croissant (v0.15.1) for a hallucination-resistant commentary pipeline

## Findings
- [likely] Jhamtani et al. 2018 (ACL, P18-1154) 'Learning to Generate Move-by-Move Commentary for Chess Games from Large-Scale Social Forum Data' collected 11,578 annotated games / 298K move–commentary pairs from the GameKnot forum. Commentary is labelled into categories Description, Quality, Comparison, Planning, Contexts, General (General = player/tournament info needing external knowledge). Their model is usually called GAC (Game-Aware neural Commentary): an LSTM generator over hand-crafted game-state features such as 'move threats and evaluation scores' / 'ongoing attacks'. Human study rated outputs close to ground truth only on the 'direct move description' subset. Later work notes preprocessing files are missing from the released code.  
  src: https://aclanthology.org/P18-1154/ ; https://github.com/harsh19/ChessCommentaryGeneration ; secondary: https://arxiv.org/pdf/2410.20811
- [likely] The GAC dataset is noisy and stylistically heterogeneous ('commentary varies widely in style and often relies on pragmatic context'); only the move-description category is reliably grounded in the board, which is the root reason later papers abandon BLEU-style evaluation.  
  src: https://2018.aclweb.org/paper/1085/ (abstract); https://arxiv.org/pdf/2410.20811 (critique of BLEU for commentary)
- [likely] Zang, Yu, Wan 2019 (ACL, P19-1597) 'Automated Chess Commentator Powered by Neural Chess Engine' (code: github.com/zhyack/SCCOfficial, repo now 404) trains a neural chess engine (board encoder + move prediction + position value), pre-trained on expert games and self-play, jointly with category-specific generators for five categories: Description, Quality, Contexts, Comparison, Planning. Secondary summaries report the 'SCC-strong' variant got best BLEU-4 in Comparison (3.05), Contexts (6.21), Quality (18.87) — i.e., absolute BLEU is tiny; gains were largest in categories needing look-ahead (Comparison, Planning, Contexts). Motivation quote: external engine features 'are not in a continuous space'.  
  src: https://aclanthology.org/P19-1597/ ; https://arxiv.org/pdf/1909.10413 ; https://sotaverified.org/papers/190910413
- [likely] Lee, Wu, Dinan, Lewis 2022 'Improving Chess Commentaries by Combining Language Models with Symbolic Reasoning Engines' (arXiv 2212.08195) conditions BART on symbolic engine output with controllable commentary types (Move Description, Move Quality, Move Comparison, Game-State); human judges preferred it over Jhamtani's GAC at least 72% of the time. Kim et al. 2024 criticise it for only sorting moves into categories (excellent/good/inaccuracy/mistake/blunder) 'without deeper insight into the decision'.  
  src: https://arxiv.org/pdf/2212.08195 ; https://arxiv.org/html/2410.20811v2
- [verified] ChessGPT (Feng et al., NeurIPS 2023, arXiv 2306.09200; code github.com/waterhorse1/ChessGPT) trains ChessGPT-Base/Chat and ChessCLIP on a mixed game+language corpus; the README names free sources pathtochessmastery, pgnlib, gameknot, lichess_studies and paid megabase/chess_publishing, filtered with fastText language-ID. The README states no dataset size, no eval task list and no limitations; the paper proposes an evaluation framework for LLM chess ability. Treat as a data/model resource, not a grounded commentary method.  
  src: https://arxiv.org/abs/2306.09200v1 ; https://github.com/waterhorse1/ChessGPT
- [verified] Kim et al. (NAACL 2025, arXiv 2410.20811) 'Bridging the Gap between Expert and Language Models: Concept-guided Chess Commentary Generation and Evaluation' propose CCC: concept vectors are extracted (01_probing_svm.py, SVM probes) from LeelaChessZero T78 activations using Stockfish 8 concept labels over 200K Lichess positions (plus STS and lichess-puzzle derived 'other concepts'), the move-relevant concepts are prioritized and fed to an OpenAI LLM (02_ccc_generation.ipynb); GCC-Eval (03_gcc_eval.ipynb) is an LLM judge with dimensions relevance, completeness, clarity, fluency plus an expert-model accuracy check, and correlates better with humans than BLEU/ROUGE. Their framing: LLMs produce fluent commentary but hallucinate because of weak chess decision-making. A later automatic eval table scores GAC at correctness 0.63 / relevance 0.46 / completeness 0.15 / clarity 0.66 / fluency 0.64 with 8.9 words per comment.  
  src: https://aclanthology.org/2025.naacl-long.481/ ; https://github.com/ml-postech/concept-guided-chess-commentary ; https://arxiv.org/html/2410.20811v2
- [likely] 'Hallucinations on the Board: Tool-Augmented Evaluation of LLM Chess Commentary' (Hebbar, Sheng, Oh, Viswanath, arXiv 2608.04240, Aug 2026) introduces ACT-Eval: commentary is split into atomic claims that are routed to engine-backed tools and expert gold references, scoring factual correctness, conceptual coverage and move-quality judgment; benchmark of 325 position–move pairs (125 with expert gold atoms) and a five-class error taxonomy. Headline: GPT-5.4 without tools produced incorrect sub-claims 22.0% of the time; smaller open-weight models >40%; tool access clearly improves factual correctness and move-quality assessment, but coverage of expert strategic/tactical ideas stays limited for all models. They show a hallucinated commentary scoring 4.9/5 under GCC-Eval while 2 of 3 main claims were factually wrong (LLM-as-judge shares the domain weakness). Limitation: LLM atomization can drop context and cause false rejections.  
  src: https://arxiv.org/abs/2608.04240 ; https://www.alphaxiv.org/abs/2608.04240

- [likely] 'Do Chess Explanations Reflect Model Decisions? Behavioral and Token-Level Tests of LLM Reasoning Faithfulness' (Parfenova, arXiv 2609.22245, BlackboxNLP@EMNLP 2026): fluent explanations can shift action preferences while providing 'only limited evidence of faithful reasoning'; 'linguistic plausibility, consistency with a generated action, and solution correctness are distinct properties'. A related survey (arXiv 2609.18286) separates existence, strategic correctness and faithfulness of explanations: 'Linguistic fluency can create a strong impression of understanding even when the underlying chess analysis is incorrect or weakly grounded.'  
  src: https://arxiv.org/pdf/2609.22245 ; https://arxiv.org/pdf/2609.18286
- [verified] ChessQA (Wen, Tang, Anderson, U Toronto, arXiv 2510.23948, Oct 2025; code github.com/CSSLab/chessqa-benchmark) benchmarks LLM chess understanding in five categories with item counts Structural (1,100: capture/control/protect relations), Motifs (600: detector-defined geometric relations, e.g. absolute pin), Short Tactics (900: Lichess puzzle first move / mate-in-one), Position Judgment (500: Stockfish 16 eval bucket at 100k nodes), Semantic (400: comment relevance judged by an LLM); finds 'persistent weaknesses across all five categories'. Answers are verified deterministically (attack relation, absolute-pin definition, canonicalized UCI).  
  src: https://github.com/CSSLab/chessqa-benchmark ; https://arxiv.org/pdf/2510.23948
- [likely] State-tracking failures: Toshniwal et al. (AAAI 2022, arXiv 2102.13249) show transformers trained on move sequences can track pieces/legal moves only with large data and full history access (approximating full attention causes 'a significant performance drop'); Harang et al. (ICML 2025, arXiv 2508.19851) propose a model-agnostic evaluation that compares the legal-move set implied by the model's believed board state with the true one and report that 'LLMs struggle to keep coherent internal models over long sequences'. An unverified ChessBench blog claims giving Claude Opus the legal-move list raised its legal-move rate from 8% to 73% and top models forfeit up to 8.5% of games to illegal moves.  
  src: https://ojs.aaai.org/index.php/AAAI/article/view/21390 ; https://arxiv.org/abs/2508.19851 ; https://jso.eecs.yorku.ca/wp-content/uploads/2026/07/chessbench-llm-failures-1.pdf (unverified)
- [likely] Ruoss et al. (NeurIPS 2024, arXiv 2402.04494, 'Amortized Planning with Large-Scale Transformers', formerly 'Grandmaster-Level Chess Without Search') release ChessBench (10M games, 15B Stockfish-16 action/state values); a 270M-param searchless policy reached ~2895 Lichess blitz Elo — but 'perfect distillation is still out of reach'. Relevance: strong move-prediction networks exist, but none of this yields verifiable explanations.  
  src: https://arxiv.org/abs/2402.04494v2
- [verified] Maia (McIlroy-Young et al., KDD 2020, arXiv 2006.01855): nine Lichess rating bins 1100–1900 (Glicko-2), one model per bin; Maia matches human moves >50% of the time and accuracy grows with skill, higher than Stockfish/Leela which 'do not predict human moves well'; a separate network predicts whether a human will blunder next move. Maia-2 (Tang et al., NeurIPS 2024, arXiv 2409.20553; pip install maia2, MIT, CSSLab/maia2) is a single model with 'skill-aware attention' conditioned on both players' ratings; inference API: model.from_pretrained(type='rapid'|'blitz'), inference.inference_each(model, prepared, fen, elo_self, elo_oppo) -> move_probs dict + white_expected_score ('not a calibrated win probability'); batch columns ['board','move','active_elo','opponent_elo']. Case study: P(correct mate-in-1) rises from ~0.22 at 1100 to ~0.45 at 1900. README now says 'Maia-3 is recommended for new projects'. Per-bucket accuracy tables were not retrievable.  
  src: https://maiachess.com/blog/introducing_maia ; https://arxiv.org/abs/2409.20553 ; https://github.com/CSSLab/maia2 ; https://pypi.org/project/maia2/
- [likely] Take Take Take's production chess coach (AI Engineer Europe 2026 talk 'Building a chess coach') uses exactly the facts→narration split: Stockfish evaluates, deterministic 'detectors identify relevant chess features' (threats, candidate moves, forks, pins, pawn weaknesses, strategic plans), the LLM 'converts signals into explanations without being trusted to calculate the chess itself', and Maia probabilities 'distinguish the objectively strongest continuation from an unusually difficult or instructive decision'. Reported latency 'sub 3 seconds on Gemini Flash' (unverified social post). Negative user reports feed a Slack-connected agent that proposes prompt/detector changes under human review.

- [likely] McGrath et al. 'Acquisition of Chess Knowledge in AlphaZero' (arXiv 2111.09259; PNAS 2022) train sparse linear probes on AlphaZero activations for a Stockfish 8 concept set of 93 concepts from Stockfish's public API (evaluation terms such as material, mobility, king safety, threats, passed pawns, space) plus programmatic custom concepts (e.g., pawn forks, knight forks, isolated pawns, doubled pawns, each for 'mine'/'opponent'), producing what–when–where plots; material emerges early, king safety later. Follow-up Schut et al. (PNAS 2025, arXiv 2310.16410) extract novel AZ concepts and teach them to four world-champion-level GMs via puzzles (proof of concept). Relevance: concept vocabularies for commentary can be defined as programmatic board predicates; probing is a research tool, not a product component.

- [likely] Interpretability of Leela: Jenner et al. (NeurIPS 2024, arXiv 2406.00877) find Leela internally represents future optimal moves (probe predicts the move two turns ahead with 92% accuracy on single-best-line positions). 'Three-Body Alignment' (arXiv 2607.21993) shows GM rationales, engine-assisted commentator rationales and LLM rationales form distinct embedding clusters; reranking toward human rationales costs tactical strength. 'Communicating Chess Strategies in Natural Language' (Cui, Ling, Ng, NUS, arXiv 2607.11486, Jul 2026) defines 'chess strategy verbalization' from engine-derived strategies (Stockfish 16 / Fairy-Stockfish, gpt-oss-120b) and concludes strategies must be evaluated beyond the main line, pure concept-based descriptions have limits, and LLM evaluators have limits.  
  src: https://arxiv.org/abs/2406.00877v1 ; https://arxiv.org/pdf/2607.21993 ; https://arxiv.org/abs/2607.11486
- [likely] Recent 'explain while playing' models: Queen (Bhaskar, Cheng, Chen, Princeton, arXiv 2610.03695, Oct 2026) couples a frozen Leela BT5 encoder with SmolLM3-3B via cross-attention, explanations contain a best-move recommendation, a predicted principal variation and prose linking them, trained by iterative search distillation (1782→2697 Lichess-scale Elo); evaluation of explanation quality is LM-based. 'Grounded Chess Reasoning via Master Distillation' (Tang et al., U Toronto, arXiv 2603.20510, Mar 2026) distils Stockfish (depth-24 PVs, multi-PV vs best-only ablation) into a 4B chain-of-thought model C1 (48.1% puzzle accuracy). Neither includes an external claim verifier in the snippets available.

- [likely] Barthelemy, 'Chess variation entropy and engine relevance for humans' (arXiv 2505.03251, May 2025): entropy of the principal variation measures line complexity; non-experts do poorly on high-entropy lines, most pronounced when |eval| < 100cp (about two-thirds of positions); argues tools should communicate line complexity, not just the score.

- [verified] Lichess puzzle generator criteria (ornicar/lichess-puzzler generator/generator.py + util.py, verified): win_chances(score) = 2/(1+exp(−0.00368208·cp))−1 (mate → ±1); candidate position when score ≥ Cp(200) and win_chances(score) > win_chances(prev) + 0.6, or mate_soon (Mate(15)); rejected if prev_score > Cp(300) (already winning) or if score < Cp(400) and material_diff(winner) > −1; skipped when castling rights not maximal or < 2 legal moves. A solver move is an 'only move' (is_valid_attack) if there is no second PV, or TB only_winning_move, or valid mate-in-1 (second best win_chances ≤ 0.6), or win_chances(best) > win_chances(second) + 0.7 (multipv=2 via get_next_move_pair); solution continues while best.score ≥ Cp(200); trailing moves trimmed until line ends on an attacker move with a second-best; length-1 puzzles discarded; is_repetition(2) aborts.

- [verified] Lichess puzzle theme tagger (ornicar/lichess-puzzler tagger/cook.py, python-chess, verified) is the de-facto open-source motif detector. Indexing: mainline[0] is the opponent's setup move, mainline[1::2] solver moves. Detectors and algorithms: fork = non-king move to a square not in a bad spot that attacks >1 opponent non-pawn pieces each worth more than the mover (king_values) or hanging and not defended; hanging_piece = first solver capture of a piece that was hanging, not a mere recapture of equal/greater value, and (line < 4 plies or material_diff at ply 3 ≥ value at ply 1); skewer = solver ray-piece capture where the opponent's previous move started on the line between from/to, that piece was more valuable than the one captured, and the target is in a bad spot; pin_prevents_attack = pinned opponent piece (board.pin ray ≠ BB_ALL) attacks a solver piece off the pin ray worth more or hanging; pin_prevents_escape = pinned piece worth more than the attacker on the ray, or hanging and having pseudo-legal moves leaving the ray; discovered_attack = discovered_check, or solver capture whose previous solver move started on the line to the target without landing on it (not castling); discovered_check = check from a piece other than the one that just moved; double_check = >1 checkers; sacrifice = material_diff drops ≥ 2 vs initial after a solver move (not if opponent promotes); x_ray = capture through a square the opponent and solver both just moved to, opponent's start square between from/to; trapped_piece = util.is_trapped before the capture; attraction = solver move captured by K/Q/R on the same square, then that square attacked and (king captured or captured again); deflection = capture/promotion after opponent and solver shared a destination or a check, target attacked from opponent's old square and not from its new one; interference/self_interference, intermezzo (recapture square not defended by the recapturing piece; capture legal two plies earlier), clearance (prior solver move vacated the square/line a ray piece now uses), capturing_defender (captured a piece that was defending the capture square), exposed_king (opponent king beyond rank 4 with no pawn shield and later checks), quiet_move (non-check, non-capture, non-attacking, non-advanced-pawn, non-king move), defensive_move/check_escape (≥3 legal moves, final move non-forcing), back_rank_mate (king on home rank, three squares in front occupied by own unattacked pieces, checker on the rank), smothered/anastasia/hook/arabian/boden-doubleBishop/dovetail mate patterns, mateIn1..5, advancedPawn, promotion/underPromotion, enPassant, castling, piece endgames. overloading is hard-coded `return False` (never produced).  
  src: https://raw.githubusercontent.com/ornicar/lichess-puzzler/master/tagger/cook.py

## Implications
- Architecture must be facts → selection → narration → validation, with the LLM never asked to compute chess. Every published system that works (Take Take Take, TNG, DecodeChess, CCC) feeds engine + deterministic detectors to the LLM and treats it as a verbalizer; every system that lets the model reason about the board (GAC, ChessCoach, Queen, raw GPT) is 'often wrong' (ChessCoach README) or ~22–40% incorrect sub-claims (ACT-Eval).
- Facts layer (deterministic, engine-independent, from chessops/shakmaty): per position compute side to move, check/checkers, pinned pieces (ctx().blockers / shakmaty pins) with pin rays, attackers/defenders per square with x-ray defence (tagger is_defended removes enemy sliders), hanging pieces (is_hanging), bad-spot pieces (attacked and hanging or attackable by lower-value piece), trapped pieces (is_trapped), forks after the move (attacked opponent non-pawns worth more or hanging, ≥2), skewers/discovered attacks/discovered checks via ray/between against the previous move, material balance and captured-piece lists, pawn structure predicates (passed/isolated/doubled, advanced pawn), king shelter/exposed king, back-rank weakness (own pieces on the three squares in front of a home-rank king), castling rights, phase (phase.ts), opening name, tablebase category, master-explorer frequencies, clock/time-trouble, novelty.
- Facts layer (engine, per position, already available via MultiPV=2 report): White-POV cp/mate/wdl for best and second-best, PVs in SAN, delta of win% caused by the played move, 'only move' criticality using the lichess-puzzler rule win%(best) − win%(second) ≥ 0.7 on [−1,1] (≈35 points) or a softer app threshold, mate created/lost per lila Advice, and 'threat' (null-move) analysis via swapMove to state what the opponent would do if allowed. Add an engine probe of the played move's refutation: after a ?/?? move, the next position's best line is already the refutation (analysis[i].best[0]); for 'why the better move' use analysis[i-1].best[0] PV. Consider optional per-piece attribution from Stockfish 'eval' (NNUE derived piece values).
- Human-likelihood facts: Maia-2 (MIT, pip, rapid/blitz) gives move_probs conditioned on elo_self/elo_oppo; use it (a) to phrase 'a player at your level usually plays X here' and (b) to grade difficulty of the best move (low Maia probability + large engine gap = instructive/hard moment vs obvious blunder). It is Python/PyTorch, so it would be an optional sidecar or future ONNX port — not a core dependency.
- Selection layer: rank facts per node by salience (eval swing, criticality, motif value, mate threats) and emit a bounded, typed FactSet (JSON) — this is what makes the LLM output checkable. Encode the lichess puzzle-theme keys as the motif enum so themes line up with the puzzle DBs already in the app (db/schema.rs themes table) and with user vocabulary.
- Narration layer: two interchangeable backends behind one interface — (1) deterministic templates driven by i18next keys (offline fallback; pattern already used for 'Blunder. Nf3 was best.' by lichess and for Coach text by chess.com), (2) optional LLM provider (Claude API key in settings) that receives ONLY the FactSet plus the SAN/FEN and must cite fact IDs; prompt it to produce short per-move text and a game narrative built from per-phase summaries (opening name → first deviation/novelty → turning points by win% swing → endgame/tablebase). Do not pass raw PGN and ask for analysis.
- Validation layer (ACT-Eval-style, local): split LLM output into claims that reference squares/pieces/moves; verify each against the board (piece on square, legal move, attacked/defended, check, capture), against engine facts (sign/direction of eval changes, 'wins material', 'forced mate'), and reject or regenerate sentences with unverifiable claims; enforce that every SAN mentioned parses in the correct position (chessops parseSan). Also enforce 'no move ideas beyond the PV unless marked as a fact'. Treat LLM-as-judge as insufficient (ACT-Eval's 4.9/5 hallucination example).
- Explain complexity, not just the score: incorporate PV entropy / number of near-best alternatives (bestMovesFamily already filters lines within 10 win%) and Maia difficulty so commentary can say 'only move' vs 'several good moves' (Barthelemy 2025; chess.com 'Great Move' notion).
- Data model: add a structured, versioned commentary record per node (facts, selected facts, text, provenance: template|llm model id, validation status) rather than only writing into node.comment; persist text into node.comment and highlights into node.shapes ([%csl]/[%cal]) so PGN export works unchanged; keep the structured record in the tree store or a sidecar keyed by FEN+ply so it survives republish and is diffable in tests.
- Backend placement: motif detection can live in Rust (shakmaty, fast, testable with #[cfg(test)] FENs, exposed via a new tauri_specta command that returns typed facts, bindings auto-generated) or in TS (chessops, reusable for live analysis without IPC). The LLM call should go through Rust reqwest (no capability allowlist change, keys never touch the webview) or add the provider URL to capabilities/main.json if done from TS. Store the API key via a new secure mechanism (tauri-plugin-stronghold or OS keyring) rather than the localStorage precedent used for the lichess token.
- Glyph policy: extend getAnnotation to emit 'Miss' (⊗) when the opponent's previous move lost >X win% and the reply failed to keep ≥Y of it, and 'Only move' (□) when criticality holds; keep thresholds aligned with chess.com's 5/10/20 expected-point bands (already matched) and document the lichess 15/10/5 mapping.
- Evaluation plan for the interview/upstream story: build a fixture set of positions with expected facts (ports of tagger/test.py cases and ChessQA-style structural checks), unit-test every detector, and measure the narration backend with an ACT-Eval-like claim verifier over a sample of games — report % verified claims and coverage of ground-truth motifs, not BLEU.

## Open questions
- ACT-Eval's five error classes and exact tool list (arXiv 2608.04240) could not be read; arxiv.org, alphaxiv, papers.cool, aclanthology, PMC, HF and most mirrors are DNS-blocked in this sandbox. Needs direct reading before adopting their taxonomy.
- Exact feature set of Jhamtani's GAC model (which threat/attack features, which engine score) and Zang's engine-to-generator encoding are known only from secondary summaries; the ACL PDFs were unreachable.
- Kim et al. CCC: the concrete concept list (Table 6), the concept-ranking rule per move, the prompt format, and the CCC vs GPT-4o vs human numbers were not retrievable; only the repo pipeline (Lc0 T78 + Stockfish 8 + SVM probes + OpenAI) is verified.
- McGrath et al. concept list: '93 Stockfish 8 concepts + custom concepts' is from a search snippet; the full tables (2–4) were not read.
- Maia-1 per-bin move-match percentages and Maia-2 overall accuracy numbers were not retrievable; only qualitative claims (>50%, grows with rating) are supported.
- Harang et al. (ICML 2025) quantitative results per model and the accuracy-vs-game-length curve were not read.
- Chess.com Coach text generation internals (is it templated or LLM-based as of 2026?) is undocumented; only user complaints and the Classification V2 bands are known. chess.com domains are blocked here.
- No open-source Rust motif-detection crate was found; shakmaty attack APIs (attacks_to, pins) were not inspected in this session — verify method names before designing the Rust facts module.
- Whether Stockfish's current release still prints 'NNUE derived piece values' from the 'eval' command in the same format (verified only for the 2021 commit), and whether other UCI engines support it (they do not), so per-piece attribution would be Stockfish-only.
- Google 'ChessCoach' as named in the task does not appear to exist; the only ChessCoach found is Chris Butner's open-source engine. 'Explaining Stockfish' and 'ChessLLM commentary' as paper titles were not found; nearest matches are Kim et al. 2024, Lee et al. 2022, ACT-Eval 2026, Cui et al. 2026.
- How en-croissant's report stores depth/score for variations added from the PV (createNode leaves score null) — relevant if commentary wants evals along the refutation line; may require an extra engine pass or using cloud-eval.
- Secure secret storage: no stronghold/keyring dependency exists; adding one is a new dependency decision for upstream maintainers.
- Maia-2/Maia-3 are PyTorch Python packages; feasibility of shipping as an optional sidecar or converting to ONNX for a Tauri app is unassessed.
