# Answers

## [verified] What identity should per-node commentary be keyed by, and which tree mutations invalidate it?
## 0. Verdict (details and evidence below)

No node id exists. The only identity that survives every structural mutation in `src/state/store/tree.ts` with zero fix-up code is the node object itself, because all three structural mutations move existing object references instead of rebuilding nodes (`moveNode.children.unshift/push(newMoveNode)` tree.ts:593/595; `parent.children.splice(index, 1)` :646; `node.children.unshift(node.children.splice(v, 1)[0])` :668). Therefore: store commentary ON the node (an optional field, assigned nowhere by default) for the live tree, and use a content-addressed "line key" (root fen + UCI sequence, which `analyzeGame` already receives) only for async request/response correlation and caching. Do NOT key a side map by `number[]` path (the repo already gets this wrong for `headers.start` and `practicePath`) or by FEN (collides; wrong for move-centric text). A stable `id` field is a viable second choice but buys nothing over node-residency for the live tree and costs PGN pollution + test churn.

## 4. Why FEN keys are wrong for this feature specifically (verified collisions + semantic argument)

- `findFen` returns the first DFS hit (treeReducer.ts:46-54) and PracticePanel relies on it 4 times; `getTranspositions` exists because the same 4-field FEN legitimately appears at multiple paths (CompleteMoveCell.tsx:28-57, with `hasMorePriority` chess.ts:660-672 ranking them). Full 6-field FEN still collides whenever two move orders reach the same position in the same number of plies (fullmove number and halfmove clock match).
- The requested text ("why was this a mistake, what was the idea of the better move") is a function of (parent position, move played, engine best at parent, scores before/after) — i.e. of the edge/path, not the resulting position. Two transposing paths have different last moves and different "better move" context. Only "what is threatened now" is position-only. The repo already separates these: per-path data (`score`, `annotations`, `shapes`, `comment`) lives on the node, per-position engine output lives in the FEN+moves-keyed cache.

## 5. Why `number[]` path keys are what the repo already gets wrong

- `headers.start` is a persisted path (chess.ts:187-188) that `deleteMove` fixes (:654-656) but `promoteVariation` (:659-671) and `makeMove` with `mainline: true` (:593) leave stale.
- `practicePath` (:85-86) is never adjusted by any mutation.
- `getNodeAtPath` (treeReducer.ts:172-181) never returns null despite `getNode`'s `TreeNode | null` type (tree.ts:28): on an out-of-range index it returns the deepest existing node (:175-176). A stale path therefore resolves to a WRONG BUT VALID node — exactly the "commentary silently attaches to the wrong move" failure.

## 6. Concrete design implications

A. Live storage: optional node field (e.g. `commentary?: {...}` on `TreeNode` treeReducer.ts:16-28), not assigned in `createNode`/`defaultTree` → survives M1–M3 with no code, dies correctly on M4, survives sessionStorage (M6), zero fixture churn. `deleteMove` (:645) and `addAnalysis` (:746-754) already prove identity/move-based lookup inside immer drafts works. Mutators follow the `setScore` pattern tree.ts:478-487 (`getNodeAtPath(state.root, path)` then assign); choose `dirty` semantics deliberately — `setScore` sets `dirty = true` (:481) though engine-derived, `clearShapes` sets it only on actual change (:508-510), `setReportInProgress` never does (:496-502).
B. Async correlation (LLM/engine request → response): capture the line key `getVariationLine(root, path, true)` chess.ts:148-170 (or the node reference) at request time and resolve the target node at response time by walking moves/SAN, NOT by stored `number[]` — otherwise the feature inherits the `addAnalysis` index-alignment race (tree.ts:702-808 vs chess.rs:449-453).
C. Semantic staleness (content, not key): commentary inputs change on `addAnalysis` (:709 `cur.score`, :732/:798-803 annotations, :791 new best-move sibling), `setScore` (:478-487), `setAnnotation` (:422-442). Store an input fingerprint next to the text (e.g. `${parent.fen}|${n.san}|${score(parent)}|${score(n)}|${bestUci}`) and regenerate on mismatch — a per-node analogue of `getTreeStructureHash` (treeReducer.ts:183-194). FEN keys do not help here; the inputs are edge-local.
D. PGN round-trip decision is separate from keying: either (i) don't persist (like `depth`), accepting loss on M5 and on file reload, or (ii) persist via `getMoveText`/`innerParsePGN` using either plain `comment` text (interoperable, but merges with user comments and is markdown-rendered by Comment.tsx) or a custom `[%...]` markup (survives per chess.ts:403-404 evidence; must be stripped for display; pollutes exports). If a stable id is ever wanted it must ride the same channel or it dies on M5.
E. Variations: `addAnalysis` scores/annotates only mainline nodes (:806) and the nodes it inserts (:760-791) carry no score; commentary for variation nodes needs its own data source regardless of key.
F. Multi-tab scoping: any side map must be per store (per `tab.value`, BoardsPage.tsx:309) as `engineMovesFamily` is (atoms.ts:544-548); node-resident storage gets this for free.

## Bottom line for the architect
- Deterministic fallback with today's backend: exactly `≤2` lines per mainline position plus the next position's `best[0]` (= played-move eval/refutation), nothing for the final position or off-mainline nodes, no threat lines.
- With Option A (~a refactor of chess.rs:545-597 plus one command), the fallback can request arbitrary extra facts per move (threat line, N candidates, eval after a hypothetical move) without disturbing `engine_processes`; cost is one process spawn per request unless Option B's pool is added.
- "Explain this position" in the live view is feasible without disturbing running engines only via such a new command (or the `analyze_game`-with-empty-`moves` workaround); `get_best_moves` cannot be used for it.

## [verified] What is the persistence budget and failure mode if commentary text (or retained raw MoveAnalysis[]) is stored in TreeState? (En Croissant v0.15.1, TreeState JSON-written to sessionStorage per tab via debounced zustand persist)
## 1. Direct answer

There is NO persistence budget in the repo: nothing measures, caps, partializes, prunes or guards the per-tab TreeState written to sessionStorage, and nothing in the repo handles `QuotaExceededError`. The only "budget" is whatever the host webview's sessionStorage quota is (not determinable from the repo; see open questions). The failure mode is an uncaught exception inside a `setTimeout` callback that leaves the dirty-write queue intact, retries (and re-throws) after every subsequent mutation in any tab, and silently stops persisting some or all tabs; because inactive tabs are unmounted (`keepMounted={false}`), sessionStorage is the ONLY copy of an inactive tab's state, so a stalled flush means switching tabs / reloading loses everything since the last successful write.

## 2. The persistence pipeline, exactly as coded

- Store creation: `src/state/store/tree.ts:516-523` — `createStore<TreeStoreState>()(persist(stateCreator, { name: id, storage: createDebouncedSessionStorage<TreeStoreState>() }))`. No `partialize`, no `onRehydrateStorage`, no `migrate`, no `version` (grep of `src/state/store/tree.ts` for `onRehydrateStorage|migrate|partialize` returns nothing). zustand's default `partialize: (state) => state` (persist.ts:191 of zustand 5.0.11, locked at `pnpm-lock.yaml:4084`) means the WHOLE `TreeStoreState` (`root`, `headers`, `position`, `dirty`, `report`, `practicePath`, plus action functions that JSON.stringify drops) is queued on every `set()`.
- Every action in tree.ts uses the persist-wrapped `set` (zustand persist.ts:236-240: `set(...args); return setItem()`), so every mutation — including pure navigation like `goToNext` that only changes `position` — enqueues a full-state snapshot.
- `src/state/store/debouncedStorage.ts:65-68` — `setItem` puts `{state, version}` (the object, not a string) into a module-global `pendingWrites: Map<string, StorageValue<unknown>>` (`:4`) and calls `scheduleFlush(300)`. `scheduleFlush` (`:21-30`) clears and re-arms ONE global timer for all stores — it is a debounce, not a throttle, so a stream of mutations < 300 ms apart in any tab defers all flushes.
- `flush()` (`:9-19`):
  ```ts
  for (const [name, value] of pendingWrites) {
      sessionStorage.setItem(name, JSON.stringify(value));
  }
  pendingWrites.clear();
  ```
  No try/catch. Serialization happens here (so cost is paid at flush time, for every pending key).
- Hydration: `getItem` (`:56-64`) returns the pending in-memory object if present, else `JSON.parse(sessionStorage.getItem(name))` with no try/catch. zustand wraps `getItem` in `toThenable(...).catch(e => postRehydrationCallback?.(undefined, e))` (persist.ts:270, 333-339); with no `onRehydrateStorage` configured the error is swallowed and the store keeps `defaultTree()` → a corrupted/absent key becomes a silent empty board. zustand 5.0.11 only writes back on hydrate when a migration ran (persist.ts:308-310), so mounting a tab does not itself enqueue a write.
- Unload: `bindFlushHandlers` (`:32-50`) flushes on `beforeunload`/`pagehide`; same unguarded `flush()`.

## 3. Who shares the quota (one origin, one document)

The Tauri app has a single window (`src-tauri/tauri.conf.json:70-76`); in-app "tabs" are React components inside one document (`src/components/tabs/BoardsPage.tsx:252-262`), so ALL of the following share one sessionStorage area:
- One key per tab id for the tree store (`tree.ts:519`, `name: id`, id from `genID()` at `src/utils/tabs.ts:89-94`).
- Direct raw writes of the same shape `{ version: 0, state: tree }`: `src/utils/tabs.ts:123` (createTab with pgn), `src/components/tabs/ImportModal.tsx:112`, `:165`, `:187`, and the string copy in `duplicateTab` at `BoardsPage.tsx:115-117`.
- jotai atoms on sessionStorage: `tabs` (`src/state/atoms.ts:58-62`), `activeTab` (`:64-68`), `expanded-directories` (`:70-74`), `database-conversion-state` (`:254-265`), `database-view` (`:267-271`), plus the zustand `database-view` store (`src/state/store/database.ts:195-198`), and `lichess_player_alias` (`src/components/home/Accounts.tsx:93`).
- CRITICAL budget fact: closing a tab never removes its key. `closeTab` (`BoardsPage.tsx:47-72`) filters `tabs`, kills engines and aborts the game but never calls `sessionStorage.removeItem(value)`; the only `removeItem` callers in `src` are the lichess alias (`Accounts.tsx:83`) and the storage adapters' own methods (`debouncedStorage.ts:69-72`, `src/state/utils.ts:55-57`) which nothing invokes for tree keys (grep for `persist\.`/`clearStorage` in `src` returns nothing). The only wipe is the menu action `Help > Clear saved data` → `sessionStorage.clear()` at `src/routes/__root.tsx:291-293`. A new store is created and re-hydrated from sessionStorage/pendingWrites on every activation. sessionStorage is therefore the primary store for inactive tabs, not a cache.

## 4. Failure mode on QuotaExceededError, step by step

1. Some mutation enqueues a snapshot; 300 ms later `flush()` iterates `pendingWrites` in insertion order and `sessionStorage.setItem` throws on the first key that crosses the quota (`debouncedStorage.ts:15`). Note the throwing key need not be the big one — any key written after the area is nearly full fails, including a small tab's key.
2. The throw escapes the `setTimeout` callback (`:26-29`). No React error boundary sees it (TanStack Router's `defaultErrorComponent` at `src/App.tsx:77` only covers render errors); no `window.onerror`/`unhandledrejection` handler exists (none in `src/index.tsx` (read in full), `src/App.tsx`, `src/routes/*`). Result: console error only; UI keeps working on in-memory state, so the user sees nothing.
3. `pendingWrites.clear()` (`:18`) is never reached, so every pending entry stays in the Map. Keys before the failing one in insertion order were written; the failing key and everything after it were not.
4. `flushTimeout` was already nulled (`:27`), so the next `setItem` from ANY tab re-arms the timer; the next flush rewrites all retained entries (wasted work) and throws again at the same key. This is an infinite retry/throw loop, one console error per idle-300 ms after any mutation anywhere, until the area shrinks (user deletes content, or `Clear saved data`).
5. Consequences for data:
   - While the page lives, `getItem` prefers `pendingWrites` (`:57-60`), so switching back to a tab whose write failed still restores the in-memory snapshot — EXCEPT for keys that get flushed successfully later: those are deleted only via `clear()` after a fully successful flush, which can't happen, so in practice the Map keeps growing to one entry per touched tab (memory, not loss).
   - On `location.reload()` (menu `View > Reload`, `__root.tsx:263`, Ctrl+R) or window close: `beforeunload`/`pagehide` call the same `flush()` (`:37-44`); it throws at the same key; every key after it is lost; reload restores those tabs to their last successfully written snapshot (possibly their creation-time state from `tabs.ts:123`), or to `defaultTree()` if the key never existed.
   - `closeTab` decides the "unsaved changes" prompt from sessionStorage, not from the live store: `JSON.parse(sessionStorage.getItem(value) || "{}")` then `tabState.state.dirty` (`BoardsPage.tsx:51-52`). After a stalled flush, `dirty` is stale → the user can close a tab with unsaved (uncommitted) annotations/commentary without being asked. If the key never got written and the tab has a persistent origin, `tabState.state` is `undefined` → `TypeError` → the tab cannot be closed from the UI.
   - `duplicateTab` copies the raw stored string (`BoardsPage.tsx:115-116`), bypassing `pendingWrites`: it duplicates the last flushed snapshot (≥300 ms stale normally; arbitrarily stale after a quota failure) and doubles that key's footprint instantly.
6. Direct raw writers also have no try/catch and fail in distinct ways: `createTab` (`tabs.ts:123`) throws before `setTabs` (`:126`) → async rejection, tab silently not created; `ImportModal.tsx:112/:165/:187` throw inside a jotai `setCurrentTab` updater → tab not converted and the trailing `setLoading(false)` (`:198`) is skipped on the sync paths; `createZodStorage.setItem` (`src/state/utils.ts:52-54`) throws synchronously inside jotai writes for `tabs`/`activeTab` → in-memory tab list diverges from the persisted one.

## 2. What happens on a programmatic write while the editor shows that node (verified, step by step)
Setup: `AnnotationPanel` is mounted only while the "annotate" tab is selected — `Tabs keepMounted={false}` at `src/components/boards/BoardAnalysis.tsx:196`, panel at `:243-245`. `AnnotationEditor` subscribes to `s.root`, `s.position`, `s.setComment` (`src/components/panels/annotation/AnnotationEditor.tsx:18-20`) and derives `currentNode = getNodeAtPath(root, position)` (`:22`).

1. Writer mutates the store (e.g. `setComment(generated)` or any `produce` that assigns `node.comment`). immer yields a new `root`; `AnnotationEditor` re-renders; `currentNode.comment` now holds the generated text.
2. `useEditor({ ..., content: currentNode.comment || null, contentType: "markdown", onUpdate }, [position.join(",")])` (`AnnotationEditor.tsx:24-44`) is called again with the new `content`, but the deps value is unchanged.
3. In `@tiptap/react` 3.20.0: `useEditor` stores the latest options in a ref (`react/src/useEditor.ts:345-349`) and runs `useEffect(instanceManager.onRender(deps))` every render (`:361`). `onRender` (`:228-258`): because `deps.length !== 0`, it skips the `setOptions` fast path (`:235-245`, only taken for empty deps) and calls `refreshEditorInstance(deps)` (`:264-290`), which returns early when `previousDeps` equals `deps` element-wise (`:272-278`). Result: no `setOptions`, no re-creation. Nothing happens to the editor.
4. Even if `setOptions` were reached, `Editor.setOptions` (`core/src/Editor.ts:264-281`) only merges `this.options`, re-applies `editorProps` and calls `view.updateState(this.state)`; `content` is consumed exactly once, in `createDoc()` during construction (`Editor.ts:143`, `:476-480`). So the option `content` is dead after mount; the ProseMirror doc still contains the pre-write text.
5. The store and the editor are now divergent: notation (`CompleteMoveCell`/`TableNotation`, see §5) shows the generated text; the editor shows the old text (or the empty placeholder).
6. Next doc-changing transaction in the editor (keystroke, toolbar bold/heading/list, paste; NOT caret moves/focus — `Editor.ts:686-694` emits `update` only when `!preventUpdate && transactions.some(tr => tr.docChanged) && !prevState.doc.eq(state.doc)`): `onUpdate` is invoked through the always-fresh wrapper `onUpdate: (...args) => this.options.current.onUpdate?.(...args)` (`useEditor.ts:134-147`), so the *callback* is not stale, but it calls `setComment(editor.getMarkdown())` (`AnnotationEditor.tsx:39-41`) where `getMarkdown()` serialises the editor's own JSON (`markdown/src/Extension.ts:185-187`). 7. The editor resyncs with the store only when a NEW `Editor` is constructed, i.e. (a) `position.join(",")` changes (navigate away and back; `refreshEditorInstance` destroys and recreates, `useEditor.ts:280-289`), or (b) the panel unmounts/remounts (tab switch; `keepMounted={false}`; the instance is destroyed ~1ms after unmount via `scheduleDestroy`, `useEditor.ts:296-325`). ## [verified] How should a two-stage job (engine pass, then commentary) drive progress and cancellation in En Croissant, given the current ProgressStore/ProgressButton/useProgress/analyze_game/cancel_analysis plumbing, and does @tauri-apps/plugin-http fetch honour AbortController?
## 0. Short answer

There is no multi-stage job anywhere in the codebase today; the nearest thing is `download_file`'s `finalize: Option<bool>` flag (src-tauri/src/fs.rs:30,33,81-83), which lets a caller suppress the terminal `finished=true` so a later stage can finish the same progress id — but no caller passes `false`. Recommendation: drive the whole pipeline from Rust under the single existing id `report_${tab}`, make the Rust side emit a terminal progress event on EVERY exit path (ok / error / cancel), carry a `stage` on the progress event, and run the LLM stage with reqwest under the same `analysis_cancel_flags[id]` token so `cancelAnalysis(id)` actually aborts in-flight HTTP. A TS-orchestrated second stage is viable only with a module-level `AbortController` registry (plugin-http DOES honour AbortSignal — verified below) and an http capability scope change, and it inherits an existing stale-store bug when the user switches tabs.

### 1.7 Latent races/warts in the current single-stage flow (inputs to the contract)
1. Cancel leaves `{finished:false}` in ProgressStore (chess.rs:531-535 emits nothing); it is only removed because `handleCancel` calls `clear()` client-side (ProgressButton.tsx:52). Both `cancelAnalysis` (async, chess.rs:467) and `clearProgress` (sync, progress.rs:57) are fire-and-forget; a loop iteration that passed the flag check (531) but not yet `update_progress` (537) can re-insert a stale entry after `clear_progress` → next mount `getProgress` returns it → `isActive=true` → button disabled with no job behind it.
2. Any `?` error in `analyze_game` leaves the same stale entry plus a leaked cancel flag (no guard between chess.rs:485 and 633).
3. Persisted `report.inProgress=true` can be re-hydrated with no Rust job behind it (e.g. app killed mid-report, then sessionStorage survives in the webview); `showProgress` then stays true until the user clicks the cancel icon.
4. `completed = finished` (ProgressButton.tsx:38): a terminal `finished=true` always renders `labels.completed` ("Report generated"), so there is no way today to signal "ended by cancel/error" through the progress channel.

## 4. Recommended contract (derived from the above)

### 4.1 One id, Rust-owned pipeline, terminal event on every exit
- Keep the single progress id `report_${tab}` (ReportPanel.tsx:57, ReportModal.tsx:84) so `useProgress`'s mount-time `getProgress` (useProgress.ts:7-13) restores the bar after the user switches tabs — this only works if the stage that is running has Rust-side progress. A TS-only commentary stage has nothing to re-fetch.
- Either (a) a new command `generate_report(id, engine, go_mode, options, uci_options, commentary: Option<CommentaryOptions>)` that calls the engine pass and then the commentary stage, or (b) minimal change: add `finalize: Option<bool>` to `analyze_game` exactly like fs.rs:30-33, so it ends with `update_progress(.., 100.0, false)` when a commentary stage follows, and a second command `generate_commentary(id, ...)` finishes the same id. (b) has a gap between commands where `cancel_analysis(id)` is a no-op (flag removed at chess.rs:632) and relies on TS to sequence; (a) avoids both and keeps `.finally(() => setInProgress(false))` semantics intact with a single promise.
- Add an RAII guard in Rust (e.g. `struct ProgressGuard<'a> { store, app, id, done: bool }` with `Drop` that, if not `done`, emits a terminal event and removes `analysis_cancel_flags[id]`), fixing warts 1.7(1)(2) for the existing flow too. Today only chess.rs:533 and :632 remove the flag.

### 4.2 Extend the progress payload (additive; bindings regenerate via tauri-specta)
- `ProgressItem`/`ProgressEvent` are two duplicated structs (progress.rs:8-20); add to both: `stage: Option<String>` (e.g. `"engine" | "commentary"`) and a terminal status, e.g. `status: Option<"finished"|"cancelled"|"failed">` while keeping `finished: bool` for AddEngine/AddDatabase/AddPuzzle (they only read `finished`). Without a distinct cancel/fail signal, `ProgressButton` renders `labels.completed` for any `finished=true` (ProgressButton.tsx:38,57).
- `ProgressButton`: map `stage` → label (`labels.stages?.[stage] ?? labels.inProgress`), treat `status==="cancelled"|"failed"` as `clear()`+`setInProgress(false)` without `completed`. Progress value: either sub-range (engine 0-80, commentary 80-100, so the bar never sits at 100 for a minute) or per-stage 0-100 with the stage label; note the bar is hidden only when `completed` (ProgressButton.tsx:77).
- Drive `EvalChart`'s `LoadingOverlay` (ReportPanel.tsx:89 / EvalChart.tsx:172) from `stage === "engine"` only, so the eval graph appears as soon as engine results exist while commentary streams in.

### 4.3 Cancellation that reaches the LLM request
- Keep `cancel_analysis(id)` (chess.rs:465-472) as the single TS entry point (ReportPanel.tsx:34) — no UI change. In Rust, make the commentary stage observe the same token: simplest is `Arc<AtomicBool>` + `tokio::sync::Notify` (tokio "full" already present), or add `tokio-util` and switch `analysis_cancel_flags` to `DashMap<String, CancellationToken>`. Each provider call: `tokio::select! { r = client.post(url).json(&body).send() => r?, _ = token.cancelled() => { guard.cancelled(); return Err(Error::AnalysisCancelled) } }`; dropping the reqwest future aborts the connection. Between requests, check the flag like chess.rs:531.
- On cancel the Rust side should emit the terminal event itself (and/or `progress_state.remove(&id)`), so the client-side `clear()` in `handleCancel` (ProgressButton.tsx:52) is belt-and-braces rather than load-bearing, closing race 1.7(1).
- If the TS-orchestrated variant is chosen instead: hold `AbortController`s in a module-level `Map<tabId, AbortController>` (not component state — the panel unmounts, AnalysisPanel.tsx:99/BoardsPage.tsx:187), make `handleCancel` call both `cancelAnalysis(id)` and `controller.abort()`, add the provider host to `http:default` (capabilities/main.json:43-51), write a TS-side progress mirror (Rust `getProgress` cannot describe a TS stage, so add a `set_progress` command or emit from TS via a Rust passthrough), and resolve the store by tab id at completion rather than through the closure captured in ReportModal.tsx:82-103.

### 4.4 Persisted `report.inProgress`
- Because Rust ProgressStore is the source of truth and in-memory (main.rs:95), either exclude `report.inProgress` from persistence (`partialize` in tree.ts:517-522) or reconcile on mount: if `getProgress(id)` returns `null`/terminal while `report.inProgress` is true, set it false. Otherwise wart 1.7(3) persists. `ProgressButton` already clears it on `finished` (ProgressButton.tsx:42-46); it would also need to clear it on the new cancelled/failed status.
- Deliver commentary incrementally (per-ply event, e.g. `CommentaryEvent { id, ply/path, text, kind }` via `tauri_specta::Event` like `ProgressEvent`, or `tauri::ipc::Channel`), and apply it to the store looked up by tab id, so a cancelled run keeps what was written and the orphaned-store problem (1.6) is avoided.

## [verified] Can commentary safely query both the reference DB (novelty/book facts) and the user's personal DB ("your history in this line") in one session, given AppState.db_cache / line_cache / clear_games / preload_reference_db?
SHORT ANSWER: No. As of upstream v0.15.1 (package.json:3, src-tauri/Cargo.toml:3) the mmap search index cache is a single process-global slot that is never compared to the requested file, so any two different `.db3` files queried through `search_position` / `is_position_in_db` in one process lifetime WILL silently answer from whichever index was loaded first. The claims in the question are all confirmed by the code, plus two aggravating details (cross-DB id contamination, and poisoned negative cache that `clear_games` cannot evict). Fixing it is small and local (key the cache by path); a frontend "clear+preload" protocol alone is NOT safe because other in-app searchers run concurrently.

=== 1. The single-slot cache (verified) ===
- `src-tauri/src/main.rs:83-84`:
  `line_cache: DashMap<(GameQuery, PathBuf), (Vec<PositionStats>, Vec<NormalizedGame>)>,`
  `db_cache: Mutex<Option<MmapSearchIndex>>,`
  One `AppState` for the whole app: `.manage(AppState::default())` at main.rs:247.
- `MmapSearchIndex` (src-tauri/src/db/search_index.rs:214-219) is `#[derive(Clone)]` with fields `mmap: Arc<Mmap>` and `archived: &'static ArchivedSearchIndex`. It stores NO path/identity, so nothing downstream can detect which file it came from. Clone is cheap (Arc), which matters for the fix.
- Index file is per DB: `get_index_path(db_path) = db_path.with_extension("ecsi")` (search_index.rs:316-318).

`search_position` (src-tauri/src/db/search.rs:237-462):
- :244 opens a SQLite connection for the REQUESTED `file` via `get_db_or_create`.
- :265-298 obtains the index: `let mut cache = state.db_cache.lock().unwrap(); if cache.is_none() { ... MmapSearchIndex::open(&index_path) ... *cache = Some(index); } cache.as_ref().unwrap().clone()`. The `file` argument is only consulted inside the `is_none()` branch (:268 `get_index_path(&file)`). If the slot is already `Some`, `file` is ignored entirely; it does not even check that `file`'s `.ecsi` exists.
- :422 `mmap_index.par_iter().for_each(process_entry);` iterates whatever index is in the slot.

`is_position_in_db` (search.rs:464-559) is a copy of the same block at :494-527 with identical semantics; it never opens the SQLite DB at all, so its answer is 100% determined by the cached index.

`clear_games` (src-tauri/src/db/mod.rs:1899-1904): `let mut state = state.db_cache.lock().unwrap(); *state = None;` — resets ONLY `db_cache`. Grep for `line_cache` across src-tauri/src: only main.rs:83, search.rs:256 (read), :452 (insert), :479 (read), :550 (insert). There is NO code path anywhere that removes or clears `line_cache` entries; it lives until process exit.

`preload_reference_db` (mod.rs:1906-1934): generates the `.ecsi` if missing (:1914-1917), then `if cache.is_none() { ... *cache = Some(index); }` (:1919-1931). It is also a no-op if the slot is already populated — it does not replace a wrong index, so "preload" cannot be used as "switch to".

=== 2. Concrete failure scenarios for commentary ===
Let R = reference DB (e.g. masters), P = personal DB (e.g. "<user> Lichess.db3").

(a) Wrong-DB novelty. App start preloads R (src/App.tsx:136-143, called at :191). Commentary calls `is_position_in_db(P, q)` for "have you played this before?": slot is `Some(R)` -> it scans R's games and reports whether MASTERS reached the position. Conversely if P was loaded first (e.g. commentary queried P before any Database-panel search), then `analyze_game`'s novelty pass (src-tauri/src/chess.rs:615-629, `is_position_in_db(reference, GameQuery::new().position(query.clone()).clone(), state.clone())`) scans P and will flag ordinary book moves as "novelty" because the user never played them.

HOW COMMENTARY MUST TREAT IT (facts-layer contract derived from the above)
1. Never compute win-chance deltas / CPL / accuracy / "??" thresholds from a `dtz` value. Gate every numeric use on `score.value.type === "cp" || "mate"`. Make `normalizeScore` exhaustive with ts-pattern (as `formatScore` already is) so a new variant cannot silently fall through; if dtz is kept numeric anywhere, map it like mate (`CP_CEILING * Math.sign(value)`), never as raw cp.
2. Treat `dtz` as a categorical tablebase fact: sign => side-to-move-relative win/loss after color normalisation (`value * (color === "black" ? -1 : 1)`), magnitude => plies until a zeroing move. Suitable phrasing: "Tablebase: winning, N plies to the next capture/pawn move"; and compare two dtz lines by (outcome, then |dtz|), not by centipawns. The 15000/20000 vs 20000/25000 band distinction is lost by api.ts:76-87, so the facts layer cannot recover cursed-win/blessed-loss style categories from `ScoreValue` alone.
3. Carry provenance explicitly. Recommended fact shape: `{ value: ScoreValue; source: "local-uci" | "lichess-cloud" | "chessdb" | "pgn-eval" | "report"; engineId?: string; depth: number }`. Sources are determinable: engine id + `engine.type` from `enginesAtom` (schema src/utils/engines.ts:37-70, `type: "local" | "chessdb" | "lichess"`), `addAnalysis`/report = local, `%eval` = pgn. Only `local-uci`/`lichess-cloud`/`report`/`pgn-eval` are eligible for cp/mate arithmetic; `chessdb` lines must additionally be type-checked per line (chessdb returns cp for most positions, dtz/mate only in tablebase range).
4. Do not read `node.score` as "the live eval" when a remote engine may be first in `enginesAtom` (starvation above). For per-move explanations in the analysis-by-engine view, read `engineMovesFamily({ tab, engine })` for an explicitly chosen engine (prefer `type === "local"`, else lichess, else chessdb-with-type-filter). For the "Generate report" flow, `node.score` is populated by `addAnalysis` from a local engine and is safe (cp/mate only), which makes the report path the right home for the deterministic offline fallback.
5. If the feature later makes chessdb lines write `node.score` (e.g. fixing the starvation by letting the first engine with lines set the score regardless of type), the dtz branch in `normalizeScore`, `EvalChart`, and the PGN `%eval` exporter (chess.ts:85-90) must be added FIRST, otherwise dtz would be exported as `#N` mate annotations into users' PGNs.

## 4. What a commentary stage must do differently (grounded requirements)

1. Typed, discriminable errors. Do not return `crate::error::Error` for provider failures (it serializes to an opaque string, error.rs:187-203, and changing that impl would change the `E` of every `Result<_, string>` binding and every `unwrap` caller). Either (i) a dedicated `#[derive(Serialize, Type)] #[serde(tag = "kind", rename_all = "camelCase")] enum CommentaryError { Auth { status: u16 }, RateLimit { retry_after_ms: Option<u64> }, Network { message }, Provider { status: u16, message }, MalformedResponse { message }, Cancelled, NoProviderConfigured, … }` as the command's `E` (specta will generate the TS union exactly as it does for `GoMode`), or (ii) return `Ok` with a per-move tagged outcome (`{ source: "llm" | "fallback"; text } | { source: "failed"; error: CommentaryError }`) following the `DatabaseInfo` precedent — (ii) is preferable because it supports partial success + deterministic fallback, which `Result<Vec<_>, string>` (all-or-nothing, chess.rs:633) cannot express. If the provider call is made from TS instead (fetch / `@tauri-apps/plugin-http` ^2.5.7, package.json:40), map `response.status` (401/403→auth, 429 + `retry-after`→rateLimit, 5xx→provider, `TypeError`→network, zod ^3.22.4 `safeParse` failure→malformedResponse) into the same union — never the chess.com/api.tsx pattern of one generic toast. If made from Rust, check `res.status()` (unlike fs.rs:44) and classify `reqwest::Error` via `is_timeout()/is_connect()`.
2. Cancellation must be a first-class non-error (or an explicitly swallowed `kind: "cancelled"`), not `Err("Analysis cancelled")` (error.rs:93-94, chess.rs:534). Any stage that starts showing errors will otherwise toast on every user cancel. Reuse the `analysis_cancel_flags` + `cancel_analysis` mechanism (chess.rs:465-472, 485-488) but remove the flag and finalize/clear progress on EVERY exit path, not just 533/632.
3. Localize via discriminant → key, TS-side, like `chessopsError` (chessops.ts:57-73): add `Errors.Commentary.Auth`, `.RateLimit`, `.Network`, `.MalformedResponse`, `.NoProvider`, `.Unknown` (+ optional `{{detail}}` interpolation à la en-US.json:396) to en-US.json; map with ts-pattern `.exhaustive()`; always render through `t()` (avoid BestMoves.tsx:255). Rust `#[error("…")]` text is untranslatable and must only be the developer `detail`, never the headline.
4. Two-layer surfacing, both localized: a transient `notifications.show({ title: t(...), message: t(...), color: "red", icon: <IconX/> })` per Board.tsx:206-210 (NOT `unwrap`, whose title is hardcoded "Error" and which throws), plus a persistent inline state in the panel (an `Alert title={t("Common.Error")}` per AddEngine.tsx:104-108, or text per TablebaseInfo.tsx:55-59) next to the report button/EvalChart (ReportPanel.tsx:56-90) with Retry and a "fell back to offline commentary" status. Hold it in the tree store beside `report.inProgress` (tree.ts:105, 197, 496-502) — e.g. `report: { inProgress: boolean; stage?: "engine" | "commentary"; error?: CommentaryError | null }` — so it survives panel switches the way `inProgress` does.
5. Always handle all three outcomes and always clean up: `if (r.status === "error") { … }` AND `.catch` (bindings rethrow JS `Error`s, generated.ts:28; there is no global `unhandledrejection` handler) AND `finally { setInProgress(false); clear progress }`. Do not rely on `useProgress`'s `finished` flag to release the button — on an error path it never arrives and the button sticks (useProgress.ts:38 + ProgressButton.tsx:40, 72). Emit a terminal progress event or call `clear_progress` from Rust on error.
6. Log without leaking secrets. `unwrap` logs the full message to `en-croissant.log` (unwrap.tsx:11; main.rs:196-198), which users are told to open/share (src/routes/__root.tsx:300-306) and the issue template link in ErrorComponent.tsx:46. Provider error bodies/URLs may echo the API key; redact before `error()`-logging and never put the key or the raw body in toast/Alert text. fs.rs:34 (logs full URL) is the anti-pattern.
7. Keep the engine stage's contract: `addAnalysis` input type (tree.ts:74-81, `{best: BestMoves[]; novelty; is_sacrifice}[]`) is unchanged; the commentary stage consumes the same `MoveAnalysis[]` and must not be able to make the engine report fail — engine failure and commentary failure need separate `kind`s/stages so a 429 does not discard annotations.
8. Tests: there is a store test for `addAnalysis` (src/utils/tests/store.test.ts:415) but no error-path test anywhere in the report flow; make `httpStatus→kind` and `kind→i18nKey` pure functions and unit-test them.
