## Implications
- Upstream shape must be 'deterministic first, LLM strictly optional'. The only two maintainer statements on point are 'An AI model is way out of scope for this project' (#230, 2024) and 'I don't really want to add any feature dependent on paid third party APIs' (#704, 2026) — but in both threads he explicitly welcomed the underlying feature (basic move comments; TTS) when done locally/free. So: ship an offline rule-based commentary engine as the core deliverable, with an LLM provider as an off-by-default, bring-your-own-key adapter that also supports a local OpenAI-compatible base URL (Ollama/llama.cpp) so it is not 'dependent on paid third party APIs'. Never make Generate Report call a network LLM implicitly.
- Quality gate is the maintainer's stated bar: 'I'd rather have no descriptions than bad descriptions' (#230) and 'ELO prediction is very misleading' (#749). Every deterministic sentence must be grounded in a verifiable fact (engine PV, hanging/under-defended piece via SEE, mate threat, only-move gap, sacrifice flag from `is_sacrifice`), and the generator should emit nothing rather than filler. Avoid speculative or evaluative language that cannot be checked; expose the supporting line/arrows (his own prototype `getComment` returned `{text, arrows}`).
- Reuse and extend the maintainer's own abandoned design instead of replacing it: `getComment(pos, move) -> {text, arrows} | null` in the `report-comments` branch (sacrifice / attacks piece / threatens mate / fianchetto / develops). A PR framed as 'finishing #108 / #230's report-comments branch, now with better facts' matches his mental model; a parallel chess.com-clone panel (what #649 did) has no precedent of being accepted.
- Fact extraction belongs next to the existing Rust analysis: extend `MoveAnalysis { best, novelty, is_sacrifice }` (src-tauri/src/chess.rs:449-453) with structured facts (hanging pieces, threats, mate-in-N from PV, only-move margin, phase) computed alongside `qsearch`/`naive_eval`, keeping the TS side (`getAnnotation` in src/utils/score.ts:75-120) as the classifier. Keep the NL renderer a pure function of (facts, annotation, engine lines) so it can also run from live analysis `BestMoves` (addresses #637 and the maintainer's 'live analysis would be better' remark in #72).
- Persist generated commentary in `TreeNode.comment` (src/utils/treeReducer.ts:25-26) so it survives PGN export (src/utils/chess.ts:117-118), but tag it as generated (e.g. a `[%ec-gen]`-style marker or a separate `generatedComment` field) so users can clear/regenerate without losing hand-written notes; coordinate with open PR #872 (markdown source editor) which touches the same editor components.
- Network/secret handling must respect the existing architecture: the renderer's HTTP allowlist (src-tauri/capabilities/main.json:43-52) does not include any LLM host, so the LLM call should be a Rust `#[tauri::command]` using the already-present `reqwest`, with a user-configured base URL (localhost allowed). Store the API key through a dedicated Tauri store/keychain command rather than `atomWithStorage` localStorage, because issue #898 already criticises bearer tokens in the renderer; also sanitise LLM output before rendering (Comment.tsx uses rehypeRaw unsanitised per #898) — render generated text as plain text/escaped markdown.
- Privacy posture: the project ships opt-out PostHog telemetry that sends only `app_started` + version and never game data. An LLM provider sends full positions/moves off-device, which is a new category; make it an explicit opt-in in Settings > Privacy (reuse the existing 'privacy' category in SettingsPage.tsx:618-625), show exactly what is sent, and keep the deterministic path as the default for all users.
- PR strategy for a sole, bursty maintainer (0 merges May–Aug 2026, 35 open PRs, feature PRs unreviewed for months, Disservin's 'split it' feedback on #803): open an issue/discussion first (CONTRIBUTING.md asks for this) referencing #108/#230/#637/#913 and the `report-comments` branch; then submit 3–4 small PRs: (1) Rust fact extraction + cargo tests, (2) TS template renderer + i18n keys + vitest, (3) UI surfacing in ReportPanel/notation, (4) optional provider adapter. Expect merges in bursts (Nov, Jan–Apr, Sep historically); plan to develop in a fork and keep the LLM adapter as a cleanly separable module that can live in the fork if upstream declines it.
- i18n is a first-class constraint: 16 locales exist and `pnpm i18n:extract` is part of the contribution checklist. Build templates from i18n keys with interpolation (piece/square names via existing `addPieceSymbol`/format helpers) rather than English string concatenation; an English-only generator will look like a regression to translators.
- Overlap/credit: Discussion #928 (Oct 2026) proposes the same static threat/motif detector (hanging pieces, pins, skewers, forks) as a board overlay and the author offered a PR. The 'what is threatened now' fact extractor should be designed as a shared module usable by both commentary and an overlay; reference #928 in the proposal to avoid duplicate effort.
- Scope note from the data: the community wants two different things — (a) per-move labels on every move (#913, #649) and (b) explanations of why (#108, #559, #637). The maintainer has shown no appetite for (a) beyond the current NAG-based scheme and distrusts chess.com-style metrics; (b) is where the maintainer has personally invested effort. Lead with (b); treat all-move labelling as optional/off by default.
